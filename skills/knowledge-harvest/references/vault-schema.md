## Layout

Everything lives under `<vault>/Knowledge/`. The skill writes nowhere else.

```
<vault>/Knowledge/
  Patterns/ Pitfalls/ Decisions/ Tools/ Domain/ Reference/   # 6 fixed categories
  _needs-review/        # candidate / conflict / security-redaction stubs
  .ledger/
    runs.jsonl          # append-only idempotency authority (state machine)
    pending/            # optional per-run transaction files
  .state/
    evidence/<evidence_id>.json   # redacted Evidence Bundles
    plans/<evidence_id>.plan.json # persisted action plans (recovery source)
    index.jsonl                   # deterministic match index
    backups/                      # pre-update note backups (never indexed)
    harvest.lock                  # mkdir lock (write-commit phase only)
```

`build_index.py` scans only the six category folders and ignores dot-dirs,
`_needs-review`, `backups/`, `.tmp*`, and non-markdown. Do not assume Obsidian
hides dot-dirs on every platform — keep secrets out of them regardless.

## Note frontmatter schema

```yaml
---
schema-version: 1
concept-id: gemini-hook-sanitized-env      # global-flat identity key (see below)
title: "Gemini hook environment sanitization"
category: Tools                            # primary folder — NOT identity
tags: [pitfall, hook, gemini]              # cross-cutting classification
aliases: ["gemini env sentinel", "AfterAgent env"]
status: active                            # active | needs-review | deprecated | superseded
superseded-by: some-other-concept-id       # only when status: superseded
related: [stop-hook-spawn-loop]            # existing concept-ids ONLY (no fabricated links)
created: "2026-07-07"
updated: "2026-07-08"
sources:                                   # provenance ONLY — never idempotency
  - evidence_id: "…"
    unit_id: "…"
    harvested: "2026-07-08T11:14:56+09:00"
    action: update
    knowledge_confidence: high
    match_confidence: exact
---

## Current conclusion

<the authoritative current-state knowledge — a reader sees truth, not a log>

## Update 2026-07-08

### Adds
…
### Supersedes
(none)
```

- `created:` and `updated:` are **two separate keys** (never `created / updated`
  on one line — invalid YAML).
- `status` matching behavior: `active` = update-eligible; `needs-review` = not an
  automatic update target; `deprecated` = history only, never wins a match;
  `superseded` = redirect to `superseded-by` if it exists, else route to review.

## The two keys: evidence_id vs concept-id

| Key | Answers | Where |
|---|---|---|
| `evidence_id` (+ `unit_id`) | "did we already process this cycle?" | ledger (authority) |
| `concept-id` | "which durable note owns this knowledge?" | note filename + frontmatter |

- `evidence_id = stable_hash(bundle)` with volatile fields (timestamps) excluded,
  so reruns of the same cycle hash identically.
- `unit_id = sha256(evidence_id + normalized claim)`. Because the claim is LLM
  text, `unit_id` is only **opportunistically** stable — the real cross-run
  duplicate defense is **concept-id dedup** at match time. Never rely on
  `unit_id` alone.
- `concept-id` is **global-flat and category-independent**: matching scans all
  categories, so re-classifying a concept never spawns a duplicate. Generated by
  `slugify(canonical_title)` (deterministic; Hangul-only titles fall back to a
  stable hash slug, with the human phrase preserved in `title`/`aliases`).

## Ledger state machine

`runs.jsonl` is the single idempotency authority. Each unit goes through
two-phase rows so a crash is recoverable:

```
{"evidence_id","unit_id","concept_id","action","status":"planned","before_sha256","after_sha256","target_path","ts"}
{"evidence_id","unit_id","concept_id","action","status":"committed","after_sha256","target_path","ts"}
```

- `committed` = done; `apply_plan.py` skips these on resume (`already-committed`).
- `planned` without a following `committed` = interrupted → reconcile by
  comparing the target's current sha to `after_sha256` before retrying.
- `failed` rows carry a `reason` (`create-collision`, `cas-mismatch`,
  `security-redaction`, `update-target-missing`, …) and never the raw payload —
  redaction findings are stored as span hashes only.

## One global vault (not per-project)

Knowledge is asset-ized **globally**. There is a single vault — set once in the
user-level `config.toml` (`~/.claude/skills/knowledge-harvest/config.toml` for a
standard install) — and every project's harvest writes to that same
`<vault>/Knowledge/`:

- **Sources are per-project** (the harvested git diff / transcript, carrying
  `repo_root`/`git_head`); **knowledge is global** (the notes, the `.state/index`
  dedup index, and the `.ledger`).
- `concept-id` is global-flat, so the *same* concept learned in project A and
  re-encountered in project B resolves to **one note** (update, not a duplicate);
  that note's `sources[]` accumulates which project/commit contributed.
- Do NOT give each project its own vault — that would fracture the dedup index
  and defeat cross-project knowledge. Point `vault.path` at one home-level vault
  (e.g. `~/Obsidian/DevKnowledge`) and leave it fixed.

## First-run config + confirmation boundary

1. `config.toml` missing → stop. Direct the user to copy `config.example.toml`
   and set `vault.path` (one global home-level vault, per above). **Never** guess
   a vault by scanning the filesystem.
2. Echo the resolved write root (`<vault>/Knowledge/`) and get an explicit
   `proceed` before the first write, and again before enabling the hook adapter.
3. Validated config keys: `vault.path`, `limits.*`, `hook.enabled`,
   `hook.hook_allow_active_updates`.
